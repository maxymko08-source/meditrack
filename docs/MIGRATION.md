# Перенесення даних із двох старих реалізацій

Новий застосунок використовує SQLite. Старі MySQL-бази не змінюються й не
очищуються. Міграція явна: спочатку створюється JSON-знімок, потім він
імпортується до нової БД. Під час цієї роботи міграцію справжніх даних не
запускали; перевірено імпорт обох схем на ізольованих тестових знімках.

## 1. Підготовка

Виконуйте команди з кореня репозиторію після встановлення `requirements.txt`.
Зупиніть старих ботів і сервери, щоб вони більше не змінювали розклади. Збережіть
звичайну резервну копію MySQL своїм засобом адміністрування. Для експорту
бажано використати користувача MySQL, який має лише право `SELECT` на старі
таблиці. Паролі залишаються в локальному файлі `.env` і не входять до знімка.

Налаштуйте кореневий `.env` для нового застосунку: `DATABASE_PATH`, `DEVICE_ID`,
`DEVICE_SECRET` та `OWNER_TELEGRAM_ID`. Не перезаписуйте старі реквізити,
поки не зробили експорт. Виконайте:

```powershell
.venv\Scripts\python.exe -m meditrack init
```

Команда створює схему й реєструє пристрій у режимі обслуговування. Вона не
переміщує SG90 та не надсилає повідомлень.

## 2. Експорт старих таблиць

Коренева реалізація мала таблицю `medication_schedules`:

```powershell
.venv\Scripts\python.exe -m meditrack.migrate export --legacy-env .env --layout root --output legacy-root-export.json
```

Вкладена реалізація мала таблиці `users` і `schedules`:

```powershell
.venv\Scripts\python.exe -m meditrack.migrate export --legacy-env meditrack/.env --layout nested --output legacy-nested-export.json
```

Якщо реквізити старого кореневого `.env` уже перенесено в інший файл, укажіть
його шлях у `--legacy-env`. Не потрібно експортувати відсутню стару БД.
Ім'я вихідного JSON має бути новим: наявний файл не перезаписується.

Експортер відкриває `REPEATABLE READ` і
`START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY`, виконує лише читання
відомих таблиць та закриває транзакцію. Це синтаксис
[MySQL 8.0 для транзакцій](https://dev.mysql.com/doc/refman/8.0/en/commit.html).
Читання одного узгодженого знімка передбачає таблиці InnoDB, як у старій схемі.
Живий експорт із сервера MySQL у цьому середовищі не перевіряли.

## 3. Явне зіставлення власника з пристроєм

Створіть `migration-map.json`. Ключ — Telegram ID зі старої БД; значення —
ідентифікатор уже зареєстрованого пристрою:

```json
{
  "123456789": "meditrack-01"
}
```

Замініть приклад своїми значеннями. Власник пристрою в новій БД має збігатися
з Telegram ID. Система не призначає чужі персональні розклади автоматично.
Для кількох пристроїв кожен потрібно спочатку зареєструвати з його власником
і секретом; конфігурація звичайного запуску реєструє один заданий пристрій.

## 4. Імпорт

Укажіть той самий файл SQLite, що заданий у `DATABASE_PATH`. Нижче показано
приклад для значення `data/meditrack.sqlite3`:

```powershell
.venv\Scripts\python.exe -m meditrack.migrate import --snapshot legacy-root-export.json --mapping migration-map.json --database data/meditrack.sqlite3
.venv\Scripts\python.exe -m meditrack.migrate import --snapshot legacy-nested-export.json --mapping migration-map.json --database data/meditrack.sqlite3
```

Виконуйте лише команди для наявних знімків. Перед кожним імпортом створюється
узгоджена SQLite-копія `*.before-migration-XXXXXXXX.bak`; її шлях виводиться
в результаті. Імпорт відбувається в одній транзакції.

Результат містить `archived` — кількість нових архівних рядків,
`imported_disabled` — кількість доданих вимкнених розкладів і
`unmapped_preserved` — кількість розкладів без явного зіставлення пристрою.
Повторення того самого імпорту не створює дублів. Якщо рядок того самого
джерела змінився після попереднього імпорту, операція завершується помилкою
без перезапису архіву; для нової версії знімка задайте інше поле `source` у
JSON і перевірте можливі дублікати розкладів під час ручного перегляду.

## 5. Що зберігається та що потребує перевірки

- У `legacy_records` зберігається **кожний рядок кожної експортованої таблиці**:
  джерело, ключ рядка, повний JSON та час імпорту. Імена користувачів, старі
  статуси й часові поля не відкидаються. Рядки без пристрою теж залишаються
  в цьому архіві та у вихідному JSON.
- Зіставлені розклади імпортуються в `schedules` із `enabled=0` та стабільним
  `legacy_key`. Якщо обидві старі реалізації містили однаковий час, обидва
  архівні записи зберігаються; під час увімкнення потрібно обрати один.
- Старе `dispensed` не перетворюється на підтверджену нову подію: у старих
  даних немає надійної дати видачі, пристрою та фізичної комірки. Значення
  зберігається в архіві без вигаданої історії.
- Старі схеми зберігали час без часового поясу. Новий час трактується як
  **Europe/Kyiv**. Перевірте це вручну, особливо якщо старий сервер працював
  в іншому поясі; автоматичне достовірне перетворення неможливе.
- Імпортована назва — «Імпортований розклад — перевірте дозу». Старі схеми не
  містили окремої назви дози. Запишіть зрозумілу назву командою `/edit`.

У приватному Telegram-чаті перегляньте `/schedules ПРИСТРІЙ` і для потрібних
розкладів виконайте `/edit ID ГГ:ХХ НАЗВА`. Ця команда також вмикає розклад.
Потім виконайте повний цикл `/service` → спорожнення → локальне `EMPTY` →
Home → `/plan` → завантаження за планом → `/refill ПРИСТРІЙ ID_ПЛАНУ`.
Імпорт ніколи не позначає комірки завантаженими самостійно.

Експортні JSON і резервні копії містять персональні дані. Зберігайте їх
локально поряд зі своїми резервними копіями, не додавайте до Git. Відновлення
старої копії SQLite потребує повного сервісного циклу та узгодження з NVS,
оскільки механізм міг переміститися після створення копії.
