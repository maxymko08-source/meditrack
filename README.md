# MediTrack — прототип послідовного диспенсера

Вісім комірок містять по одній **вручну відміряній дозі**. ESP32 отримує від
сервера команду з унікальним ID, керує одним позиційним SG90 та повідомляє
результат. Telegram задає щоденні розклади й показує план завантаження.
Часова зона — **Europe/Kyiv**.

Основна реалізація — пакет `meditrack`. Збережено Flask та aiogram, усунено
дублювання імпортів і конфігурації. Для локального курсового прототипу обрано
SQLite: одна схема, транзакції, відсутність окремого сервера БД, просте резервне
копіювання та ізольовані тести. Старі MySQL дані переносяться лише явною
міграцією; звичайний запуск їх не змінює. Архів коду — [legacy](legacy/README.md).

Це навчальний прототип. Підтвердження `command_completed` означає завершення
програмної команди руху, а не виміряне потрапляння ліків у лоток. Фізичних
випробувань у межах цієї роботи не проводили; їхній порядок наведено в документації.

## Встановлення

Потрібен Python 3.11 або новіший. Команди виконувати **з кореня репозиторію**.
Перевірка цієї версії виконувалася на Windows із Python 3.14.

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

На Linux/macOS відповідний інтерпретатор — `.venv/bin/python`.

Якщо `.env` уже існує, доповніть його значеннями з [.env.example](.env.example),
зберігши старі `DB_*` до міграції. **Не перезаписуйте наявний `.env`.**
Для нового проєкту скопіюйте `.env.example` у `.env`.

Налаштуйте `BOT_TOKEN`, власний числовий `OWNER_TELEGRAM_ID`, `DEVICE_ID` та
випадковий `DEVICE_SECRET` завдовжки щонайменше 32 символи. Згенерувати секрет:

```powershell
.venv\Scripts\python.exe -c "import secrets; print(secrets.token_hex(32))"
```

Цей репозиторій розташований у OneDrive. Перед робочим запуском задайте
`DATABASE_PATH` як абсолютний шлях до каталогу поза синхронізацією, наприклад
`C:/MediTrackData/meditrack.sqlite3`, якщо маєте право запису до нього.
`data/meditrack.sqlite3` у шаблоні підходить для локальної несинхронізованої
копії репозиторію. Активні SQLite/WAL файли не слід синхронізувати через OneDrive.

Секрет і ID пристрою мають збігатися з налаштуваннями прошивки. Для доступу
ESP32 з локальної мережі встановіть `API_HOST=0.0.0.0`; адресою сервера у
прошивці буде IP комп'ютера, не `0.0.0.0`. HTTP допустимий лише в ізольованій
демонстраційній мережі; для недовіреної мережі потрібен HTTPS із перевіркою CA.

```powershell
.venv\Scripts\python.exe -m meditrack init
.venv\Scripts\python.exe -m meditrack run
```

`run` запускає API через Waitress, Telegram-бот і працівник сповіщень.
Для окремих процесів використовуйте три термінали:

```powershell
.venv\Scripts\python.exe -m meditrack api
.venv\Scripts\python.exe -m meditrack bot
.venv\Scripts\python.exe -m meditrack notify
```

Не запускайте одночасно `run` і ці окремі процеси. Без `BOT_TOKEN` режим `run`
може обслуговувати API, але сповіщення залишаться в черзі. Для перевірки
доступності відкрийте `http://127.0.0.1:5000/`. Особисті дані доступні тільки
через автентифіковані `/api/*` та приватний Telegram-чат власника.

Сумісні `python main.py`, `python server.py` та `python bot.py` використовують
той самий пакет. Старі команди з робочим каталогом `meditrack/` не використовувати.
Файл `meditrack/.env` залишено недоторканим, але застосунок його не читає.

## Перший демонстраційний цикл

1. Спочатку виконайте калібрування порожнього механізму за інструкцією прошивки.
2. У приватному чаті бота: `/devices`, потім `/service meditrack-01`.
3. Огляньте й спорожніть усі комірки та канал. Локально підтвердьте `EMPTY` у
   Serial Monitor; дочекайтеся Home і стану `awaiting_refill`.
4. Додайте щоденні розклади, наприклад `/add meditrack-01 08:30 Ранкова доза`.
5. `/plan meditrack-01` покаже дату, час і назву для кожної комірки 1–8.
6. Завантажте відповідні демонстраційні зразки, закрийте кришку й виконайте
   точну команду `/refill`, яку повернув бот.
7. Дози відкриватимуться послідовно. Після восьмої — новий цикл обслуговування.

## Перевірки програмної частини

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Кожен тест БД використовує тимчасовий файл; тести не читають `.env`, не
очищують робочу БД й не надсилають справжніх Telegram-повідомлень.
Точні команди генерації CAD, перевірки STL і складання прошивки наведено в
їхніх окремих інструкціях. Остаточні цифрові й фізичні обмеження зазначено у
[звіті перевірки](docs/VERIFICATION.md).
